## Recorded deviations

The engine-difference register from `parity/README.md`: differences the layout gate leaves out, each approved by the root, with negative controls in `parity/test/register.test.ts`.

- **A. SVG paint-server content.** Where: `trends-default` and `trends-weekly`, the `<rect>` inside the chart's `<pattern>` in `<defs>`. `geometry.js` skips SVG `defs`, `pattern`, `clipPath`, `mask`, `symbol`, `marker`, `linearGradient`, `radialGradient` and `filter`, with their descendants. They paint nothing where they sit. An HTML element with one of those names is kept.
- **B. Inline boxes inside an overflowing ellipsis container.** Where: `match-history-narrow-900`, the truncated friend name's `bdi`. `geometry.js` marks a row `"ellipsis"` when an ancestor has `text-overflow: ellipsis`, an `overflow-x` other than `visible`, and `scrollWidth > clientWidth`. When both engines mark a row, the gate compares its x, y and height and not its width, and counts it in `widthExempt`. The container itself is compared in full.
- **E. Scaled images each engine resamples on its own pixel grid.** Where: `season-recap-default`, the 300 by 300 px profile `img`, drawn 92.02 CSS px square at 316.54, 221.23 inside the card's CSS `zoom` of 0.8217. `geometry.js` adds `{ image: [naturalWidth, naturalHeight] }` to the row of a decoded `img`, and not to an element marked `data-parity-skip`. The tile rule leaves out the pixels inside an image's box when both engines give it the same natural size, its x, y, width and height agree within 1 device px, it is drawn at other than one device px per natural px, and its two crops agree up to a 1 device px displacement: each channel of each pixel lies within 8 levels of the range the other crop holds within 1 device px of it, both ways, and no 64 px window has more than 8% of its pixels outside that. The page budget still counts those pixels, and pixels outside the box still count in the tile rule. No raster background image appears in the app, so background images are not covered.
- **F. A focus ring in a window that is never active.** Where: `overlay-dialog-escape`, the sidebar's update button at 12, 656.75, 203 by 48 CSS px, which Escape hands focus back to. `capture.ts` records the focused element in each `.meta.json` as `focused`: its `geometry.js` path, its box, its outline width and offset, whether it matches `:focus-visible` and `:focus`, and `document.hasFocus()`. The tile rule leaves out the element's box, grown by outline width plus offset when that sum is positive, when Electron's element matches `:focus-visible` with an outline, Tauri's capture focuses the element at the same path in a document without focus, and the two boxes agree within 1 device px. The page budget still counts those pixels.
- **G. Two golden answers that are the platform's own on Windows.** Where: golden replay on Windows of the goldens recorded on macOS. `dragon:augment-icon` answers `http://asset.localhost/<path>` where the golden holds `asset://<path>`, and `app:download-update` on an unpackaged app answers "In-app update only works in the portable exe build" where the golden holds "In-app update only works once the app is in your Applications folder". Windows report run 45245943821 replayed 59 of 61 on these two. Nothing else in either answer changes, and no other channel is touched.
- **H. Chromium versions on Windows: Electron 1.2.1's against WebView2's.** Where: every Windows state. Trunk Electron 44.4.5 runs Chromium 152, and the WebView2 Evergreen runtime ran Edge 157 on the operator's laptop. on Windows, `report.ts` judges a state's pixels by comparing the Tauri capture with Electron's built renderer in the same WebView2, on the Rust commands the port reads (`capture.ts --app tauri --renderer electron --api tauri`). The reference does not replay the goldens. On Windows their day-bucketed answers differ from what the Electron app shows: 90 days played against 79 on `trends-default`, and 2 games today against 12 on `match-history-narrow-900`. The port shows what the app shows. The goldens (61 of 61) and the cross-engine layout gate hold the port's data to the app. It uses pixelmatch at threshold 0.03 with anti-aliasing counted, within 0.3% of the page, with no E1. The cross-engine layout and size gates against the Electron app still run. A failure of either counts as the engine version's only when Electron's renderer in WebView2 fails it the same way: the same elements, and every box the Tauri capture moves beyond 1 CSS px moved in the same direction within 1 CSS px, or the same image size. Anything else is a port bug. Each state records both numbers (`ruleH` in `report-win.json`). On Windows the replay also accepts `isWindowMaximized` answered by its `default` golden, a call Electron's renderer makes only there, for its own window controls (`WINDOWS_RENDERER_CALLS` in `capture.ts`).
- **Port elements marked `data-parity-skip`.** Not an engine difference but a deliberate one in the port's markup. Where Electron drew one element and the port needs a wrapper to draw the same thing in WebKit, the port marks the outer element `data-parity-skip`, and `geometry.js` records its box and leaves out what it wraps. T27's `ChampionIcon` is the case: Electron draws the portrait as one `img` with `object-view-box`, which WKWebView ignores, and the port draws a clipping span at that box with a larger `img` inside. An unmarked extra element still fails the gate.
