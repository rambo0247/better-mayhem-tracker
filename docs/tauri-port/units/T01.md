## Verify, perf. Absolute numbers for the empty shell

Measured by hand on the operator's Mac (Apple silicon, macOS 27.2), release build `bun run tauri build`, on the shell at `cd31ffe`. The machine was loaded during every timing run (load average 10 to 18), see the caveat.

| Metric | Empty Tauri shell | Electron 1.2.1 (spike README) | Rule |
| --- | --- | --- | --- |
| `.dmg` | 2.26 MiB (`du -sk` 2312 KB) | 110 MB | at most 8 MB. PASS |
| `.app` | 3.65 MiB (`du -sk` 3744 KB) | 245 MB | none |
| Idle memory, 60 s after launch, `phys_footprint` summed over the app and its WebKit GPU, WebContent, and Networking processes | 60 to 65 MB in the final build (`mem-final.txt`), 74 to 77 MB in an earlier run (`footprint-samples.txt`) | about 328 MB | at most 120 MB. PASS |
| Same processes by RSS (`ps`) | 167 to 177 MB | not measured | see below |
| Process start to window built | 257 to 305 ms unloaded, 1.1 to 1.8 s loaded | not measured | none |
| Process start to first paint | 490 ms and 550 ms (two unloaded runs, `release-launch.log`), 794 to 813 ms in `tauri dev` | not measured | none |

Method. `du -sk` on the bundle and the dmg. Memory: launch the binary, wait 60 s, take the app pid and the new `com.apple.WebKit.*` processes that appeared since launch, then read `footprint -p` and `ps -o rss` three times 10 s apart (`mem.sh`, `mem-final.txt`). First paint: the shell logs `page first-paint N ms after process start` after two animation frames, and `page load N ms after process start` on the load event.

Caveats the root must weigh.

- The idle-memory rule does not say which metric. Footprint passes with room. Summed RSS is 167 to 177 MB and would fail 120 MB. RSS counts the shared WebKit and AppKit pages that every WebKit app maps, which is why T06 sums `phys_footprint` first and reports RSS beside it. This unit applied footprint.
- The footprint total moved from 75 MB to 62 MB between two runs, mostly the WebContent process (28 MB then 16 MB). The final run's window was covered and never painted for 60 s, see next point. Rerun on a quiet machine with the window in front.
- The first-paint line needs animation frames, and a webview holds them back while its window is covered. 8 of 10 launches in a loaded, cluttered session never logged it inside 6 s, and one logged it 61 s later when the window was uncovered. The `load` line always arrives. The two clean first-paint numbers came from launches before the machine was loaded. A perf lane should launch with `open`, which activates the window, on an idle machine. Launching with `open -n --stdout` in this session did not make the paint arrive, and load times ran 2 to 5 s under load.
- Not measured because the machine was busy: the Electron figures are the spike README's, not remeasured. T06 owns that.

Folders Tauri created. `tauri dev` and the bundled app create no folder under `~/Library/Application Support`. The dev binary made `~/Library/WebKit/better-mayhem-tracker-tauri` and `~/Library/Caches/better-mayhem-tracker-tauri`. The bundled app made `~/Library/WebKit/com.better-mayhem-tracker.app` (`WebsiteData`) and `~/Library/Caches/com.better-mayhem-tracker.app` (`WebKit`). None is the `better-mayhem-tracker` folder. The owner read only the modification time of `~/Library/Application Support/better-mayhem-tracker` (no listing, no open) and saw it move from 16:24 to 21:41 while the operator's packaged app was running. The Tauri processes never touch that path, and the move is unattributed.
