## Method, and what each number can and cannot see

- **Electron source.** The v1.2.1 release assets, `gh release download v1.2.1` (`BetterMayhemTracker-mac-arm64.zip` unpacked with `ditto`, `BetterMayhemTracker.exe` on Windows). Not a local `npm run dist:mac`. The zip's `.app` is 251,096 KB by `du -sk`, which matches the spike's 245 MB. The operator's installed app is never started, signalled, or measured, and every process is picked by the pid the probe spawned, never by name.
- **Run folder and data.** Each run copies the fixture (`parity/snapshots/fixture`, or any `--data` folder) into a fresh `--user-data-dir`. In the copy only, `auto_update` is `false`, `show_release_notes` is `false`, `last_run_version` is `1.2.1`, and `auto_start*` is absent. A newer release would otherwise replace the scratch app mid-run, and a login item would write the operator's LaunchAgent label. `--data none` starts on an empty folder for a runner with no fixture.
- **Isolation, a deviation from "through run-electron.ts".** `run-electron.ts` runs the unpackaged build through Playwright with `--disable-gpu`, which is not what a player runs. A packaged app cannot load `seam.cjs` (the fuses disable `NODE_OPTIONS` and CLI inspect), so nothing would hide the League client from it. On macOS the packaged app therefore runs under `sandbox-exec` with a Seatbelt profile: `(allow default)`, deny all file access to `/Applications/League of Legends.app`, `/Users/Shared/Riot Games`, and the real data folders, and deny exec of `/bin/ps`. A process under a profile cannot start Chromium's own sandbox, so Electron runs with `--no-sandbox`. Still different from production: the GPU, the packaged code path, the network and the asar are production's, but Chromium's helper sandbox is off, and the client reads as "unreadable" rather than "closed", so the poller tries and fails `ps` where production finds no lockfile. `--isolation none` skips the profile and instead waits for no League client process. `run-electron.ts` was not used for the numbers. `perf.ts` also stops before every launch while a League game runs (`waitForNoGame`, same 30 s poll and 2 minute wait as `wait-no-game.sh`) and marks a run invalid if a game starts during it.
- **Memory.** `footprint -p <pids> -j <file>` (`phys_footprint`, what Activity Monitor calls Memory), summed over the main process and every helper, with `ps -o rss` summed beside it. Windows sums `Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate` over the tree, with working set beside it. Median of 5 samples 10 s apart, taken 60 s after first content, window up, client absent. RSS is 2 to 4 times footprint because it counts the shared system frameworks every process maps, so it is not the comparison number.
- **Attribution by public facts only.** Electron helpers are children of the spawned pid, named by `--type=` (`renderer`, `gpu-process`, `utility` with the network service sub-type). Their command lines also carry `--user-data-dir`, and any process outside the tree that carries this run's folder fails the run as a stray. A WebKit helper is an XPC service whose parent is launchd, so it counts only if it did not exist before the spawn, started at or after it, and either holds a file that names the app (the GPU helper's cache folder is named after the executable, the networking helper's `~/Library/WebKit/<bundle id>` data) or is the one expected new content helper, or the nearest by pid. More than one candidate with none tied to the app makes the run invalid as ambiguous. The helper set is frozen at first content, so a second copy of the shell started later cannot join it. No process-responsibility or TCC API is used.
- **Invalid runs record no number.** A missing main, renderer, GPU or network helper, a frozen helper that disappears, a stray, an ambiguous WebKit set, a failed `footprint` read, an app exit, a game start, or no first content in 30 s. The summary lists the reasons.
- **Launch to first content.** Spawn is `performance.timeOrigin + performance.now()` taken in the probe just before `spawn`. For Electron the probe connects to `--remote-debugging-port`, auto-attaches to every page, and injects a script that records when the first `button.group.relative.flex.w-full` (the same selector `states.ts` waits for, with a test that keeps them equal) is in the DOM with a non-empty box, then two animation frames later. The headline is the two-frame time when it arrived, else the DOM time. It cannot see what a covered window withholds: Chromium stops animation frames for an occluded window, so a covered window reports the DOM time (the run records `row-in-dom` and the page's `visibilityState`). It cannot see icons or images, which load after the row. The DevTools port opens after the window's page already exists (about 570 ms after spawn in a run), so the injected script attaches to a page that is already loading. A run is flagged when the row was already there at attach, which would make the time an upper bound. The probe adds a little memory (a DevTools server, a detached session). Each run starts from a fresh profile, so no Chromium cache is warm, but the OS file cache cannot be dropped without `sudo purge`, so launches are warm at the disk level.
- **Tauri.** `--app tauri --tauri <.app|.exe>` runs a Tauri build the same way with `BMT_PERF=1`, `BMT_PERF_LOG=<file>` and `BMT_DATA_DIR=<userdata>` in its environment. First content is the arrival time of the `first-content N ms` line (T27's build must print it when the first Match History row is in the DOM, on stdout or appended to `BMT_PERF_LOG`), falling back to T01's `page first-paint N ms after process start`, which has no rows to wait for. T01's log line is kept, because T06's method does not replace it for the empty shell. A Windows release build has no stdout (`windows_subsystem = "windows"`), so T27 must write `BMT_PERF_LOG` for Windows. Windows Tauri was not run here.
- **Interleaving.** With two apps, run `i` goes A then B on even `i` and B then A on odd `i`. Each run uses a fresh profile and waits 3 s after the previous app has gone. A true cold start (dropped OS cache) is not possible without root.
- **Spread** is (max - min) / median.

## Known-case proofs of the attribution

`attribution-proof.log` (from `bun parity/perf/prove.ts --tauri <.app>`):

- A synthetic tree of one parent and two children, two holding 150 MB touched memory, beside a decoy of 150 MB that is not in the tree. The attribution takes exactly the 3 tree processes and not the decoy. Summed footprint 316 MB against 315 MB expected, 0.3% off. The same pids through `vmmap -summary` (Physical footprint) sum to 316 MB, 0.0% apart.
- The Tauri shell resolves to its main process, GPU, networking and content helper. A second copy of the shell, which has the same bundle id and executable name and so cannot be told apart by name, makes the unfrozen probe report ambiguous instead of summing both. Under the real run the set is frozen at first content, so a copy another lane starts later cannot join it. A copy started in the window between spawn and first content still makes the run invalid and it is repeated.

## Deviations and decisions for the root

- Electron runs packaged under Seatbelt with `--no-sandbox`, not through `run-electron.ts`. Reasoning above. The root can ask for the harness variant instead, but it runs with `--disable-gpu` and is not a shipped configuration.
- `ulimit -u 200` cannot be applied here: the operator's user already runs about 490 processes, so any fork fails under that cap. The probe spawns one app and at most a few helpers per run, never injects `-r`, and kills only pids it started.
- Windows needs a fixture artifact (`parity-fixture`) to measure real first content. Nothing uploads one yet (decision E2).
- T27 needs to print `first-content N ms` (stdout, and `BMT_PERF_LOG` on Windows) for `--app tauri` to time a row. T01's `first-paint` line is kept.
- Windows Tauri was not run.
- `parity.yml` existed from T02, so T06 edits it and does not create it.
- `parity/out/perf/electron-1.2.1.json` as the plan names it is written as `electron-1.2.1-mac.json` and `electron-1.2.1-win.json`, one per platform, and is gitignored with the rest of `out/`. Appendix A gets the numbers once the operator's-Mac run exists.
