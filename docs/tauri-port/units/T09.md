## Build

- [x] Port `paths.ts`. The root is `dirs::config_dir()/better-mayhem-tracker`, which is `~/Library/Application Support/better-mayhem-tracker` and `%APPDATA%\better-mayhem-tracker`, never the Tauri identifier folder. `data/`, `backups/`, `logs/` and `asset-cache/` are made on first use, as `ensureDir` does. `BMT_DATA_ROOT` overrides the root in lane builds only, per the root's decision after T08's review. A lane build is any build whose Cargo profile is not `release` and does not inherit from it: `cfg(not(bmt_release_profile))`, which build.rs sets from Cargo's `PROFILE`. Until fix round 1 it was `cfg(any(debug_assertions, feature = "parity-driver"))`, which a profile setting flips (see Fix round 1). The parity driver cannot compile in a release-profile build (T07), so the feature needs no clause of its own. Electron 1.2.1 has no override, and in a release build one would let any process environment redirect a player's database and backups. A release-profile build compiles neither the override nor `data_guard.rs`, whatever its `debug-assertions`, and every other build compiles both, because one cfg gates them. `paths::tests::a_release_build_ignores_the_override` drives `root_for` with the release kind. `tauri-ci.yml` fails a release binary that contains the string `BMT_DATA_ROOT`, with the parity-driver build as the positive control. A local release build had no `BMT_DATA_ROOT`, `bmt-parity-driver` or `refused to start`, and the driver build had `BMT_DATA_ROOT`. An empty value counts as unset. The `Paths` value is managed state, `ctx.app.state::<Paths>()`. `app_builder` calls `Paths::resolve()` each time it builds an app, and nothing caches the root per process, so golden replay can build one app per root in one process (`tests/paths_env.rs`).
- [x] `data_guard.rs`, compiled only in lane builds. A lane build whose root is the real folder, or inside it, prints why and calls `process::exit(78)`. `Paths::at` runs it before it stores the root, and `run()` resolves `Paths` first, so nothing is created or opened before it. Since fix round 1 `Paths` keeps its `Guard` and runs it again on every folder `ensure` makes or returns (`data/`, `backups/`, `logs/`, `asset-cache/`) and on every file `data_file` and `log_file` hand out. A file with more than one link also fails when its (device, inode) is the real folder's file at the same place, which catches a hard-linked `data/matches.db`. Release builds skip it.
  - Deviation from the plan line, per the root's decision. There is no `BMT_ALLOW_REAL_DATA` escape. The guard cannot be bypassed in debug and parity builds.
  - How it resolves. It makes the path absolute and first compares the text, with `..` applied, against every spelling of the real folder. Then it walks the path with its own resolver, which follows symlinks even when they dangle, applies `..` to the folder actually reached, and gives up (and refuses) past 32 links. Before each step it compares the folder it would enter with the real folder's spellings, and when the next name is a real folder name it compares the folder it stands in with the config folder by identity (device and inode; Windows: volume serial and file index). The walk stops at the first step that would enter the real folder. Identity catches firmlinks such as `/System/Volumes/Data/private/...`, volfs paths, and an NFD spelling of the home folder. Names compare case-folded, with `to_uppercase().to_lowercase()`, so the Kelvin sign and long s fold as on APFS and NTFS. On Windows a name also drops a stream suffix (`::$INDEX_ALLOCATION`, `:$I30:$INDEX_ALLOCATION`) and trailing dots and spaces, every drive spelling is one (`C:`, `\\?\C:`, `\\.\C:`, and an admin share of this machine, `\\localhost\C$`, `\\127.x\C$`, `\\?\UNC\localhost\C$`, `\\%COMPUTERNAME%\C$`), and a path that passed is compared once more through `canonicalize` of its deepest existing folder, which resolves 8.3 short names (`BETTER~1`) and volume GUID paths.
  - Which real folders. `better-mayhem-tracker` and, since fix round 1, the display name `Better Mayhem Tracker`, as `parity/lib/real-folder.ts` refuses, under `dirs::config_dir()`, the passwd home's `Library/Application Support` on macOS (`$HOME` can move the first), and `%APPDATA%` on Windows. With none known it refuses.
  - What it looks at on disk. Correction: the round-0 record said it never stats the real folder. That was false. The old walk lstat-ed every component of the root, the real folder included. Since fix round 1 it stats the config folders' own components, the components of the path up to the real folder, and the config folder for identity, and nothing in the real folder for any spelling the text or identity checks recognize. `data_guard::tests::never_looks_inside_the_real_folder` records every path the check touches for 20 hostile spellings and fails if one is the stand-in real folder or inside it, by identity. Two spellings still cost one metadata look at the real folder, because only a look can tell: a path that names the real folder itself under another name (a volfs inode path of the real folder, a Windows 8.3 short name), and on Windows the `canonicalize` step for a spelling only Windows resolves. The hard-link test stats the real folder's `data/matches.db` (metadata only), and only when the lane's own file has more than one link, so a normal run never stats it. Nothing reads a file's contents.
  - Known limit. It is a check at resolve time. A symlink swapped in after it runs is not caught.

### For the root

- T39. The release job must run the same marker scan on the shipped binaries, both platforms: no `BMT_DATA_ROOT`, `refused to start`, `bmt-parity-driver`, `BMT_PARITY_TOKEN` or `devDependencies`. CI only scans what it builds itself.
- T11 opens the database at `paths.data_file("matches.db")`, and calls `data_file` for `matches.db-wal`, `-shm` and `-journal` before SQLite opens them, so a hard-linked sidecar cannot be written through. A hard-linked WAL could otherwise be reset by SQLite on open (inferred, not tried). T17 and T22 should take file paths in `backups/` and `asset-cache/` through the same kind of method; today only their folders are checked.
- `parity/run-tauri.ts` (T07) copies `--data` with `fs.cpSync(..., { recursive: true })`, whose `dereference` defaults to `false`, so a symlink in a data folder carries into the run root. My recommendation is that it refuse any symlink in the copy, with a `filter` that `lstat`s each entry and throws, rather than `dereference: true`, which would read the target's contents through the link. `snapshot.ts` and `fixture.ts` write plain files (inferred from their code, not checked file by file), so nothing legitimate should break. The guard now catches a link at the folder and file level the app uses, but a link deeper inside `backups/` or `asset-cache/` reaches it only once those units route files through `Paths`.
- The hostile dev build in CI compiles the crate and its dependencies a third time per runner, into `target/hostile-dev`, and the hostile release a second time, into `target/hostile-release`, with LTO off. Locally the two hostile builds took about 4 minutes on a Mac at load 80 to 100. Runner time is unmeasured.
