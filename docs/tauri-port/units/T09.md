### For the root

- T39. The release job must run the same marker scan on the shipped binaries, both platforms: no `BMT_DATA_ROOT`, `refused to start`, `bmt-parity-driver`, `BMT_PARITY_TOKEN` or `devDependencies`. CI only scans what it builds itself.
- T11 opens the database at `paths.data_file("matches.db")`, and calls `data_file` for `matches.db-wal`, `-shm` and `-journal` before SQLite opens them, so a hard-linked sidecar cannot be written through. A hard-linked WAL could otherwise be reset by SQLite on open (inferred, not tried). T17 and T22 should take file paths in `backups/` and `asset-cache/` through the same kind of method; today only their folders are checked.
- `parity/run-tauri.ts` (T07) copies `--data` with `fs.cpSync(..., { recursive: true })`, whose `dereference` defaults to `false`, so a symlink in a data folder carries into the run root. My recommendation is that it refuse any symlink in the copy, with a `filter` that `lstat`s each entry and throws, rather than `dereference: true`, which would read the target's contents through the link. `snapshot.ts` and `fixture.ts` write plain files (inferred from their code, not checked file by file), so nothing legitimate should break. The guard now catches a link at the folder and file level the app uses, but a link deeper inside `backups/` or `asset-cache/` reaches it only once those units route files through `Paths`.
- The hostile dev build in CI compiles the crate and its dependencies a third time per runner, into `target/hostile-dev`, and the hostile release a second time, into `target/hostile-release`, with LTO off. Locally the two hostile builds took about 4 minutes on a Mac at load 80 to 100. Runner time is unmeasured.
