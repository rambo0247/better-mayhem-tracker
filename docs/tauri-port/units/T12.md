## Float exactness

Every value is an `f64`. The sum runs in the TypeScript's order: six unscaled components, then the multikill, carry, and win bonuses, then one multiply by `SCALE`. `Math.max`, `Math.min`, and `Math.round` are ported with their JavaScript edge cases (`NaN` wins, signed zeros, half rounds toward positive infinity). Map semantics (SameValueZero keys, a repeated participant id keeping its slot) follow the TypeScript.

`ratio ** 1.3` is the one call where engines can differ. Evidence, measured on this Mac.

- V8 main implements `Math.pow` with LLVM libc's pow since V8 15.0, and Electron 44.4.5 ships V8 15.2.124.28. A correctly rounded pow and macOS libm's pow disagree on 282 of 200,000 random inputs in (0, 1), checked against Python `decimal` at 60 digits.
- A fixture copy crafted so 658 owners' damage ratios fall on inputs where the two disagree predicts different `score_raw` bits on 98 games. Trunk Electron's backfill of that copy (through `run-electron.ts`) matched the macOS libm prediction on 669/669 games and the correctly rounded one on 571/669. Electron on macOS therefore uses the platform `pow`, which is what Rust's `powf` calls.
- So `op_score.rs` uses `f64::powf`. On Windows that is the UCRT `pow`, which is presumably what Electron's V8 calls there too. That is unproven until lane 7 runs on `windows-latest`.

## Fix round 1, at the tip SHA the root's report names

Each fix has a test that fails at `78a7d26`. The new tests were spliced onto `78a7d26`'s code and 8 of them failed there. The ninth, the champion-class order test, has no code change behind it (log kept in the owner's scratchpad as `t12-fix1/new-tests-on-78a7d26.log`).

- Nesting (lane 10). `insert_game_full` and the score backfill used `unchecked_transaction`, which fails inside an open transaction with "cannot start a transaction within a transaction". Electron's `importGames` runs 50 inserts inside one `db.transaction`, and better-sqlite3 nests each inner one as a savepoint. `db::js::transaction` now does what better-sqlite3 does. In autocommit it runs `BEGIN` and `COMMIT`. Inside an open transaction it runs `SAVEPOINT`, then `RELEASE`, or `ROLLBACK TO` and `RELEASE` on an error, which then propagates.
  - `a_kill_midway_through_an_import_batch_leaves_none_of_it` (unix). A child process opens a transaction, inserts 50 games, and SIGKILLs itself at the 26th. After reopen 0 of 50 are stored, as the verifier saw in Electron. Without the outer transaction, 25 survive.
  - `a_caught_throw_inside_a_transaction_leaves_no_rows_for_that_game`. A null id writes a `games` row under the next rowid before its participants fail NOT NULL. The savepoint takes that row out, the outer transaction stays open, and the games before and after it commit.
  - `the_score_backfill_nests_inside_an_open_transaction`. A backfill inside an outer transaction runs, and the outer rollback undoes it.
- gameId binding. The Rust pre-check that rejected any non-integer id is gone. The id binds through `js::bind`, as better-sqlite3 binds the JavaScript value, and SQLite's INTEGER affinity decides the outcome. `game_ids_bind_as_javascript_binds_them` checks every case in the verifier's `electron-report.json`, comparing the error's `to_string()`, which is what `err.message` shows in "Import failed: ...". It also asserts that nothing is written on an error, and that every table stores the integer id on success.
  - `"123"` and `"123.0"` store 123. `" 77 "` stores 77, and `-0` stores 0.
  - `1.5`, `"abc"` and `1e20` fail with `datatype mismatch`.
  - `null` and an absent id fail with `NOT NULL constraint failed: match_participants.game_id`.
  - `true` fails with `SQLite3 can only bind numbers, strings, bigints, buffers, and null`.
  - `write_participants` (T11's `payloads.rs`) takes the bound id as a `rusqlite::types::Value` to make this work.
- Info items.
  - Fixed. `compute_owner_score(.., Some(""))` now looks nothing up, as JavaScript's falsy `""` does (`an_empty_owner_puuid_falls_back_to_champion_and_kda`).
  - Fixed. `GameDenorm.queue_id` is the bound `queueId`, so a REAL or a string reaches every participant row as Electron stores it (`queue_ids_reach_participant_rows_as_bound`). The v2 rebuild reads the stored column back as JavaScript would.
  - Fixed. The duration coercion follows `ToNumber`: `0x`, `0o` and `0b` integers, signed `Infinity`, JavaScript's whitespace set, `inf` and `nan` as `NaN`, and arrays through `join`. A hex string longer than 128 bits is rounded digit by digit, not once.
  - Recorded only. A Data Dragon class tag that names an `Object.prototype` member, such as `constructor`, gives `NaN` weights in TypeScript, because `CLASS_WEIGHTS[cls]` finds the inherited function. Rust gives the default weights. Data Dragon publishes no such tag.

## Handoffs and decisions for the root

- Champion class data is an argument (`ChampionClasses { version, classes }`), not managed state, because Data Dragon loading is T22. The round-0 record said an insert scored with empty classes is corrected by a later backfill. That holds only when the insert comes before the backfill. Electron hydrates `champion-cache.json` synchronously at startup (`src/main/dragon.ts:54-56`), so its inserts normally score with real classes. The rule for T20 and T22:
  - Every insert passes the Dragon's current classes. Pass `ChampionClasses::none()` only while no champion data exists, cached or fetched.
  - The startup backfill (`check_score_backfill`, then `lcu:games-updated` on true) runs after `wait_for_champion_data()`.
  - `inserts_must_take_live_classes_once_the_backfill_has_run` shows both orders. An empty-class insert followed by the backfill converges to Electron's score. A backfill followed by an empty-class insert keeps the wrong score, because the second backfill sees an unchanged key and returns false. The verifier measured the same on 40 fixture games. The converging order matched Electron's `player_stats` on 40 of 40 (`lane6-compare.log`). The bad order differed from Electron in `score`, `score_raw` or `score_badge` on 38 of 40.
- `db::js::transaction` is the better-sqlite3 transaction for every port of `db.transaction`. T18's `importGames` can wrap its batch in it. T11's migrations and `rebuild_participants_from_payloads` still use `unchecked_transaction`. That is correct only where Electron never calls them inside an open transaction, which this round did not check.
- `/deslop` and `/no-comments` are not installed; their rules were applied by hand.
