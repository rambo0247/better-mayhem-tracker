### ICU4X data version, round 1

ICU4X 2.4's compiled data is CLDR 49 and Unicode 18. Electron 44.4.5 ships ICU 78.2 with CLDR 48 and Unicode 17. The root's every-code-point sweep on 2.4 found 196 adjacent pairs that collate differently from Electron. All of them involve 326 code points unassigned in Unicode 17, 26 of which 2.4 treats as fully ignorable. For example `"Josh\u{10EC9}"` against `"Josh"` gives Electron 1 and 2.4 gives 0.

ICU4X 2.3's data crates say CLDR 48.2.1 and ICU 78.1rc, which is Unicode 17. 2.2's say CLDR 48.2.0 and ICU 78.1rc. So c38416b pins `icu_collator` 2.3.1, the patch that fixes a Burmese contraction panic, plus `icu_decimal` and `icu_locale_core` 2.3.0. Every other ICU4X crate resolves to 2.3, `icu_provider` to its 2.3.1 patch. The 2.4 changelog has nothing this unit calls beyond the data update. Its `icu_normalizer` soundness fix is in `split_normalized_utf8` and `normalize_utf8`, which `icu_collator` 2.3.1 does not call (grep of its source). Its sort-key byte change does not matter, because the app makes no sort keys. Its Hangul change in `push_decomposed_starter` (#8484) is the one that could touch `compare`. 1,526 of the recorded pairs below hold precomposed Hangul, and all of them match Electron on 2.3.1.

On c38416b, `locale_compare` matches Electron's recorded `localeCompare` on every set the root and T15 recorded (`BMT_COLLATION_CASES`):

- the root's 196 pairs that 2.4 got wrong;
- the root's 978 pairs over unassigned code points;
- the root's 15,999 recorded pairs;
- T15's 8,742 pairs.

The remaining gap is ICU 78.1rc's data against Electron's 78.2, and CLDR 48.2.1 against 48.0. No recorded pair separates them. T39 should re-record these sets, and the 84-locale number check below, whenever Electron's ICU moves, then pin the ICU4X release whose data matches.

### Number formatting, round 1

`intl::format_integer` is `icu_decimal` at default options: the locale's numbering system, its grouping and minimum grouping digits, and its minus sign. Against the verifier's record of Electron 44's main-process `n.toLocaleString(l)`, for 84 locales and 13 numbers each:

- fc3d043's hand table: 46 of 84 locales match.
- f9d93fb, on ICU4X 2.4: 80 of 84 match.
- c38416b, on ICU4X 2.3: 80 of 84 match. `toLocaleString(undefined)` matches `format_integer(n, None)` for all 13 numbers. Node 26.8.1's full ICU (78.3, CLDR 48) agrees with 2.3 on all 84 locales and all 13 numbers.

The four that differ from Electron:

| locale | Electron | ICU4X 2.3 (CLDR 48.2.1) | Node, full ICU 78.3 (CLDR 48) | ICU4X 2.4 (CLDR 49) |
| ------ | -------- | ----------------------- | ----------------------------- | ------------------- |
| fr-CH  | `1 234 567` (U+202F) | `1'234'567` | `1'234'567` | `1'234'567` |
| eu-ES  | `1,234,567` | `1.234.567` | `1.234.567` | `1.234.567` |
| nn-NO  | `1,234,567` | `1 234 567` (U+00A0) | `1 234 567` (U+00A0) | `1 234 567` (U+00A0) |
| gl-ES  | `1,234,567` | `1.234.567` | `1.234.567` | `1 234 567` (U+00A0) |

The CLDR version is not the cause of any of the four on 2.3. Node has Electron's CLDR 48 and agrees with ICU4X. Electron writes fr-CH as French does and the other three as root does, which is what a fallback looks like when a locale's number data is missing. Chromium builds ICU from a filtered data set, so I infer that Electron's `icudtl.dat` lacks number data for these locales. The file still lists all four in its main-tree `res_index`, so the trimming is inside the bundles, and I did not decode it. gl-ES was the one CLDR 48 to 49 difference on 2.4, where Galician's group separator moved from `.` to U+00A0. The 2.3 pin removed it.

Matching Electron here would need the list of locales whose number data Chromium drops. That takes an Electron probe over every CLDR locale. See the notes for the root.

### Binary size, round 1

Release `better-mayhem-tracker-tauri`, `cargo build --release --bin better-mayhem-tracker-tauri`, strip, LTO, and `opt-level = "s"` as configured, on one target dir. LTO drops ICU code nothing calls. On this branch only the recap calls `intl`, and nothing calls `locale_compare` until T15's `teammates.rs` lands. So a scratch build also measured each head with a `main.rs` that calls `locale_compare`, which stands in for the restacked app.

| head | what it adds | bytes | with a `locale_compare` caller |
| ---- | ------------ | ----- | ------------------------------ |
| fc3d043 | before this round | 5,763,696 | |
| 2662d76 | T15's `intl`, `Collator::try_new` | 5,763,696 | 6,953,440 (+1,189,744, T15's figure) |
| b8c5505 | `icu_decimal`, every locale | | 6,970,032 (+16,592) |
| f9d93fb | root-only collation | 5,813,376 (+49,680) | 6,028,160 (+264,464, +4.6%) |
| c38416b | ICU4X 2.3 instead of 2.4 | 5,813,392 (+49,696) | 6,028,176 (+264,480, +4.6%) |

- `icu_decimal` with every locale's symbols costs 16,592 bytes next to the collator, or 49,680 bytes on its own, where it also brings the locale fallback data. That is small, so every locale stays. Electron's `systemLocale()` returns the OS regional format, which can be any CLDR locale.
- The collator's tailorings for every locale were most of T15's 1.19 MB. `CollatorBorrowed::new_root`, behind `icu_collator`'s `unstable` feature, links only the root data. It is the crate's own trim, with no generated data and no `ICU4X_DATA_DIR`. With it, the collator costs about 215 KB, and the restacked app should come out near 6,028,176 bytes. The 2.3 pin changes the size by 16 bytes.
- `new_root` agrees with Electron's `localeCompare` on every recorded set (see the ICU4X data version section).
- `intl::collator(locale)` is gone, and with it T15's `a_locale_tailors_the_order` test. Nothing called it outside that test. A tailored order, for example if T39 finds that Windows collates in the user's locale, would bring back `Collator::try_new` and the 0.9 MB.
