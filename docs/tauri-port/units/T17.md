## Build

- [x] `initDatabaseWithRecovery` runs before anything reads the database. A database that is damaged (`SQLITE_CORRUPT` or `SQLITE_NOTADB` on open, in migrations or in `quick_check`, or a `quick_check` that reports a problem) is renamed `matches.db.corrupt-<stamp>`, its `-wal` and `-shm` removed, and the newest backup that verifies is copied in. A database that is missing while backups exist takes the same path, the empty file the open made included. The report carries `problem`, `restoredFrom`, `quarantined`, and `detail`, with `detail` absent on the missing path, as Electron serializes it.
- [x] `quick_check` reads every row before taking the first, as better-sqlite3's `pragma()` does. Damage that stops the check part way then fails with SQLite's own message (`database disk image is malformed`) instead of the rows before it. The scenario diff caught this.
- [x] Backups use rusqlite's online backup on the live connection, 100 pages a step, written to `<name>.part`, verified with `quick_check` and a game count no lower than the source's, switched to `journal_mode=DELETE`, then renamed. A failure removes the `.part` and its `-journal`, `-wal` and `-shm`. Electron's full-disk run leaves nothing behind. Tauri left `<name>.part-journal` until this round.
- [x] Names are `matches-<YYYY-MM-DDTHH-MM-SS>-<reason>.db` in local time, not the plan's `<ISO>`. That is what Electron 1.2.1 writes. `parseStamp` follows V8: days 1 to 31 in any month roll forward, `24:00:00` is the next midnight, other out-of-range fields read as 0, and DST gaps and overlaps resolve as JavaScript's `Date` does. The wall time is computed with plain day arithmetic. Past jiff's year-9999 limit the offset comes from the same time 400 years earlier (a whole number of weeks, so the calendar and the zone's standing DST rule repeat), and results beyond V8's ±8.64e15 ms read as 0. The prune's week and month keys use the same shift.
- [x] Pruning keeps the newest 5, the newest of each of the last 4 weeks (Sunday-started), and the newest of each of the last 6 months. Listing sorts names first, as Node's sorted `readdir` does, so ties on the same second keep Electron's order.
- [x] The schedule checks at launch and every hour, and backs up when the newest snapshot is more than 24 h old and `auto_backup` is not `"false"`. `pre-restore` (and T18's `pre-import` and `pre-repair` through `Backups::backup_quietly`) honor the same setting. Manual backups do not.
- [x] `backup:list`, `backup:create`, `backup:restore`, and `backup:recovery-report` are ported. Restore emits `lcu:games-updated` on success.

### Deviations, each with its reason

- One lock serializes backups and restores, as Electron's single `inFlight` promise does. A list also takes it. Electron's list does not wait, but then a list during a running prune could stat a file the prune is removing. The only visible effect is that a list issued during a backup returns after it, with the new file.
- The launch check runs on a `backup-schedule` thread, registered as a Tauri plugin so it also runs in golden replay. The thread takes the lock before `app_builder`'s build finishes, so no command can list the folder before the launch snapshot lands. The window does not wait for the backup.
- A backup holds the database lock for the whole copy, about 25 ms on the fixture. Electron interleaves other statements between steps. A write that arrives during a backup waits for it, so the snapshot always passes `integrity_check` (lane 9's concern).
- File system errors read as Node writes them: `<CODE>: <description>, <syscall> '<path>'`, with ` -> '<dest>'` for `copyfile` and `rename`. The restore and recovery copy, both renames, the `stat` after a backup, and the backups folder's `mkdir` use it. The codes come from libuv's `uv_translate_sys_error` (`src/unix` errno values, `src/win/error.c` for Win32), the messages from `util.getSystemErrorMap()` measured in Node 26. An errno libuv does not map reads `UNKNOWN: unknown error`, as Node prints it. SQLite errors use SQLite's message, as better-sqlite3 does.
- A backups folder that can't be made throws Node's `EACCES: permission denied, mkdir '<path>'` into `backup:list` (a rejection), `backup:create` and `backup:restore` (`{ success: false, error }`), and recovery (the app's open error, after the damaged file is set aside, in Electron's order). The hourly check and the missing-file check swallow it, as Electron's `readBackups` does.

### Deliberate departures from Electron, which loses data in both

These two were the root's decisions. Each departs from Electron 1.2.1 on purpose.

| Case | Electron 1.2.1 | Tauri |
| --- | --- | --- |
| Restore with six or more backups, the source among the ones a seventh would prune | The `pre-restore` snapshot's prune deletes the restore source. The copy then fails with `ENOENT: ... copyfile '<source>' -> '<data>/matches.db.incoming'`, and the database stays closed: every later backup, restore and query answers `The database connection is not open` until relaunch. | The prune spares the restore source and drops the next candidate instead. The restore succeeds. |
| A restore whose copy fails (a full disk) | Same closed database for the rest of the session. The `-wal` was already deleted before the copy. | The swap copies first, then removes the `-wal` and `-shm`, then renames. A failed copy removes its `.incoming`, the untouched database opens again, and the error is Node's text. |
| Launch with the database locked by another process, read-only (`chmod 444`), or 16 KB of disk free | Sets the healthy file aside as `matches.db.corrupt-<stamp>` and restores the newest backup over it, reporting `problem: "corrupt"` with `database is locked` or `attempt to write a readonly database`. On a full disk the window never opens. | The file is left as it is. The error is logged (`Database failed to open, left as it is: ...`) and becomes the app's open error, as a read-only data folder already did: no `Database` state, and commands answer `The database connection is not open`. |

A missing file still takes Electron's path, whatever the open error, since nothing is lost by restoring. One consequence for the root: a valid SQLite file that fails migrations with a plain `SQLITE_ERROR` (say `no such table`) is now an open error every launch, where Electron would set it aside and restore. That is what the rule says. Widen the rule if that case should recover.
