### Deviations, each with its reason

- One lock serializes backups and restores. Electron's single `inFlight` promise queues only backups, not restores, so this lock does not match it (see the departures). A list also takes it. Electron's list does not wait, but then a list during a running prune could stat a file the prune is removing. The visible effect is that a list issued during a backup returns after it, with the new file.
- The launch check runs on a `backup-schedule` thread, registered as a Tauri plugin so it also runs in golden replay. The thread takes the lock before `app_builder`'s build finishes, so no command can list the folder before the launch snapshot lands. The window does not wait for the backup.
- A backup holds the database lock for the whole copy, about 25 ms on the fixture. Electron interleaves other statements between steps. A write that arrives during a backup waits for it, so the snapshot always passes `integrity_check` (lane 9's concern).
- File system errors read as Node writes them: `<CODE>: <description>, <syscall> '<path>'`, with ` -> '<dest>'` for `copyfile` and `rename`. The restore and recovery copy, both renames, the `stat` after a backup, and the backups folder's `mkdir` use it. The names and messages are generated (see Error tables). An errno libuv does not map reads `UNKNOWN: unknown error`, as Node prints it. SQLite errors use SQLite's message, as better-sqlite3 does.
- The backups folder is made as Node's recursive `mkdirSync` makes it (`MKDirpSync` in `src/node_file.cc`). A mkdir that fails with anything but ENOENT, EACCES, ENOSPC, ENOTDIR or EPERM is followed by a `stat`, and the `stat`'s error is the one thrown. A dangling link therefore reads `ENOENT ... mkdir`, not EEXIST, and a missing folder on a read-only volume reads `ENOENT`, not EROFS. On Windows a mkdir that fails `ERROR_INVALID_NAME` or `ERROR_DIRECTORY` reads EINVAL, as libuv's `fs__mkdir` sets it.
- Removing a `-wal`, `-shm`, `.incoming`, `.part` or pruned backup is `fs.rmSync(path, { force: true })` with Node's errors, measured in Node 26.8.1 on this Mac (`fix2/node-rm.json`, `fix2/node-rm-erofs.jsonl`). A missing file is no error. The JavaScript `lstat` fails first as `ENOTDIR: not a directory, lstat '<p>'`, a folder reads `Path is a directory: rm returned EISDIR (is a directory) <p>`, and the C++ remove fails as `EPERM, Operation not permitted: <p> '<p>'`, `EACCES, Permission denied: <p> '<p>'`, `ENOTEMPTY, Directory not empty: <p> '<p>'`, `ENOTDIR, Not a directory: <p> '<p>'`, or for anything else `, Unknown error: <strerror> '<p>'` (a read-only volume gives `, Unknown error: Read-only file system '<p>'`). Electron 44 bundles Node 24.21.0, whose `RmSync`, `MKDirpSync` and `ErrnoException` are line for line the ones in Node 26.8.1 (diffed from the two tags' sources), and both bundle libuv 1.52.1. On Windows, Node reports a permission failure as `EPERM, Permission denied`; the Win32 errors that count as one are MSVC STL's `errc::permission_denied` set (5, 12, 16, 19, 32, 82, 998), read from `stl/src/syserror.cpp`. That mapping is unmeasured.
- A backups folder that can't be made throws Node's `EACCES: permission denied, mkdir '<path>'` into `backup:list` (a rejection), `backup:create` and `backup:restore` (`{ success: false, error }`), and recovery (the app's open error, after the damaged file is set aside, in Electron's order). The hourly check and the missing-file check swallow it, as Electron's `readBackups` does.

## Error tables

`tauri/scripts/uv-errors.ts`, run with `node scripts/uv-errors.ts <libuv src/win/error.c> <windows-sys crate dir>` in Node on macOS, writes `src-tauri/src/backup/uv_errors.rs` and runs rustfmt on it. It refuses Bun and other platforms. Rerunning it at this tip reproduces the file byte for byte (sha1 `3c2623c1`).

- macOS: the 65 errnos `util.getSystemErrorMap()` names in Node 26.8.1 (libuv 1.52.1), each with its message. They equal the verifier's `errmap` entry for entry. libuv's own codes, getaddrinfo's at -3000 and below included, are left out of the errno table but keep their messages.
- Windows: the 100 cases of `uv_translate_sys_error` in libuv 1.52.1's `src/win/error.c`, sha256 `c804f3da...`, identical to the verifier's `libuv-win-error.c` and to the file at the `v1.52.1` tag. The Win32 values come from `windows-sys` 0.61.2's constants. Messages for the Windows-only names (`ECHARSET`, `EOF`) come from the same map.
- Linux is not a target, so other Unix systems name no errno and print `UNKNOWN`.

Where the port's Windows calls are not libuv's, a code can differ. Read from the sources at this toolchain's std commit `137d1d49` and libuv 1.52.1, none measured on Windows:

- `rename`. libuv calls `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`. Rust's `std::fs::rename` calls the same, and only when it fails `ERROR_ACCESS_DENIED` opens the source for `DELETE` and retries with `SetFileInformationByHandle(FileRenameInfoEx)` and POSIX semantics. Where that retry succeeds, which its source comment says is for a read-only file, Rust renames where Node answers `EPERM`. Where it fails `ERROR_DIR_NOT_EMPTY`, Rust reports `ENOTEMPTY` where Node reports `EPERM`.
- `copyfile`. libuv calls `CopyFileW` and Rust `CopyFileExW`, so the error codes match, but a failed Rust copy leaves its partial target where libuv removes it (measured on macOS above; the swap removes it itself).
- `mkdir`. Both call `CreateDirectoryW`. libuv reads `ERROR_INVALID_NAME` and `ERROR_DIRECTORY` as EINVAL, and `mkdirp` does the same.
- `stat`. libuv queries the handle with `NtQueryInformationFile`, Rust with `GetFileInformationByHandle` and a `FindFirstFileExW` fallback on a sharing violation, so a file another process holds can stat where libuv fails, or the reverse.
- `rm`. Node uses MSVC's `std::filesystem::remove`. The port's `std::fs::remove_file` calls `DeleteFileW` and, on `ERROR_ACCESS_DENIED`, retries ignoring the read-only attribute.
