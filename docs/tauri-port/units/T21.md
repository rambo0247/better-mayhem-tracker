## Design

The port follows `live.ts` and `challenges.ts` function for function. The parts that are new:

- **The data shapes.** `LiveTracker` holds the last snapshot (built at construction, as the module-level `emptySnapshot()` is), the record cache, the game whose map is written, and the poll task under one mutex. The one-at-a-time flag is an `AtomicBool`. `ChallengeTracker` holds the one refresh in flight as a `Shared` future, and the pending captures as a set of ids compared as a JavaScript `Set` compares them. `Tracking` holds both trackers and the one status listener.
- **The seams.** The client is T20's `Client` trait. The game's API is a `GameApi` trait, which `HttpGameApi` implements. `TrackingEnv` supplies the database, the clock (T08's `Clock` in the app), Dragon's champion and spell data, and the two events. Tests run on stand-ins with tokio's paused clock.
- **Status listeners.** Electron's listeners run inside `setStatus`. Here one task reads T19's change broadcast and calls live, then challenges, in Electron's registration order.
- **Port 2999.** Electron requests it with `rejectUnauthorized: false`. `HttpGameApi` does the same: rustls with a verifier that accepts any chain and any name but still checks the handshake signatures. It only ever connects to 127.0.0.1. Where the request goes is decided by `GameApiTarget::from_env`:
  - A `parity-ca` build reaches only the fake live client's port in `BMT_PARITY_LIVE_PORT`. With none named, every request fails as a refused connection and no socket opens, as the seam's redirect to port 1 does. The constant 2999 does not exist in a `parity-ca` build.
  - A debug build reaches no game unless `BMT_ALLOW_REAL_LEAGUE=1`, as T19's discovery does.
  - A release build uses 2999.
- **JavaScript semantics.** `||`, `??`, `Number()`, `String()`, `trim` (U+FEFF stripped, U+0085 kept), `for...of` over strings and non-iterables, `Object.values` key order, `Map` and `Set` by SameValueZero, stable sorts, and `JSON.stringify` number printing (T11's `js::stringify`) follow JavaScript. better-sqlite3 binds every number as a double, and so does this port.
- **T24.** `is_game_running` and `is_match_underway` are ported for the updater.

## Findings for the root

- **Port 2999 TLS.** The plan's first choice, the pinned Riot root during a real game, needs a real game, which the rules forbid. The port turns checks off as Electron does, so Appendix C should record that. The audit raised a risk that only a real game can settle: if the game's server offers only cipher suites rustls lacks (no ECDHE), every 2999 request fails, the page stays on "starting", and `isGameRunning` still reads true. Lane 7 settles it.
- **The connect-time event order** in `challenges-loaded`, above. It needs a synchronous status hook in T19's `StatusCell` if the root wants Electron's order.
- **T22's GameAssets has no client fallback.** With the network blocked, Electron's asset layer fetched `cherry-augments.json` and `summoner-spells.json` from the client at startup. Rust's `GameAssets` is still built with `NoClient`, which T22's record leaves to T20's restack. Spells resolved the same in these runs, because the fixture's cache holds them.
- **Contract types.** These come from T08's types, and T21 cannot change them alone:
  - `LiveEvent.id` is `i64`, but Electron falls back to the float `EventTime` when `EventID` is missing.
  - `level`, `kills`, items, ids, and `completedChampionIds` are `i64` where hostile input could be fractional or NaN.
  - A NaN `queueId` is `null` here and NaN in Electron's IPC.
  - `LiveEvent` serializes `text` before `tone`, where Electron writes `{id, time, tone, text}`. This only shows if key order is compared.
  - A falsy non-string `mapTerrain` (0 or false) answers `null`.
  - `readStored` deserializes into the typed `ChallengesData`, so a stored payload of another shape answers `null` where Electron passes it through. The payload shape has not changed since 1.0.0.
- **serde_json** also rejects a lone surrogate escape or `1e400`, which `JSON.parse` accepts. Such a body counts as no answer.
- **T03's `run-electron.ts`** sets `SEAM_FIXED_TIME` after the caller's `seamEnv`, so a lane cannot move Electron's clock through `seamEnv`. `t21-run.ts` moves the exported `FIXED_TIME` instead.
- **The opt-in tests and tools.** `against_the_parity_fake_client` and `seeded_states_answer_as_electron_did` need T21's tools in the gitignored `parity/out/T21/tools/`: `t21-run.ts`, `record-scenarios.ts`, `compare.py`, `golden-events.py`, `rows.sh`, `requests.py`, `perf-batch.sh`, and `perf.py`. The root decides whether any of them belong in `parity/`.
- **The status listener** is a tokio task reading T19's broadcast. Electron's listener runs inside `setStatus`. Only the interleaving with other async work can differ, as above.
