## What landed

- `tauri/src-tauri/src/autostart.rs` ports `autostart.ts` by hand, per E7.
  - macOS writes `~/Library/LaunchAgents/com.better-mayhem-tracker.app.autostart.plist` byte for byte as Electron does, with `<bundle>/Contents/MacOS/<exe> --hidden` and RunAtLoad.
  - Windows writes the HKCU Run value `better-mayhem-tracker` as Electron's `setLoginItemSettings` does. The data goes through a port of Electron 44.4.5's `AddQuoteForArg` (`shell/common/command_line_util_win.cc`), which gives `"<exe>" --hidden` for any exe path. Enabling deletes the StartupApproved value and disabling deletes both values, as `Browser::SetLoginItemSettings` (`shell/browser/browser_win.cc`) does. Registry failures are ignored, as Electron ignores them.
  - `auto_start_path` records the last registered target. A launch rewrites only an entry that moved, so a player who disabled the app in Task Manager stays disabled.
  - `LoginItems` names where entries go. `System` is the user's LaunchAgents under `HOME` (Node's `os.homedir()` reads `HOME` first, and so does `dirs`) and HKCU. `At` is a scratch folder and scratch HKCU subkeys. `Recorded` lists writes for golden replay on any OS. It has the same shape as T09's `Effects`, which this unit does not edit, so the next T09 merge stays trivial.
- `tauri/src-tauri/src/shortcut.rs` ports `shortcut.ts` with the `windows` crate. The process takes AppUserModelID `com.better-mayhem-tracker.app` through `SetCurrentProcessExplicitAppUserModelID`. `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Better Mayhem Tracker.lnk` is rewritten unless it already targets this exe with that id. The id is written as `VT_LPWSTR`, as Chromium's `InitPropVariantFromString` does. After a save it releases the link and calls `SHChangeNotify` with `SHCNE_UPDATEITEM` when the file existed and `SHCNE_CREATE` when it did not, with `SHCNF_PATH | SHCNF_FLUSH`, as Chromium's `CreateOrUpdateShortcutLink` does (`base/win/shortcut.cc:206`).
- `install_location::exec_path()` is Electron's `process.execPath`. That comes from libuv's `uv_exepath`, which `realpath`s on macOS (`src/unix/darwin.c`) and returns `GetModuleFileNameW` as is on Windows (`src/win/util.c`). So the port canonicalizes `current_exe()` on macOS and Linux and leaves it alone on Windows. `mac_app_bundle()` and the registered file name both use it.
- `commands/settings.rs`: `setSetting("auto_start")` now registers the login item, which closes T11's W2. `autostart:supported` answers `install_location::has_durable_install()`.
- `lib.rs`: setup sets the app id, checks the shortcut, and syncs the login item before the window opens.
- `tauri.conf.json`: `mainBinaryName` is `Better Mayhem Tracker`.
- `Cargo.toml`: `windows =0.62.2`, the version already in the lock, with the Registry, Shell, COM, and property-store features. No new crate version.
- `parity/autostart-golden.ts` records Electron's output. `parity/autostart-review.ts` runs the macOS lanes and renders the review media.
- Outside the section, approved by the root: `parity/run-tauri.ts` and `.github/workflows/tauri-ci.yml`, because `tauri build` moves the binary to `mainBinaryName`. `tauriBinary()` takes whichever name exists, the newer when both do, and names both when neither does (`parity/test/tauri-binary.test.ts`, 5 tests). All four `exe=` lines in tauri-ci.yml follow a `tauri build` and take the new name.

## Is the registered path Electron's?

- macOS: yes. Electron registers `<bundle>/Contents/MacOS/` plus `basename(process.execPath)`, where `process.execPath` is resolved through `realpath`, and electron-builder names that executable `Better Mayhem Tracker`. Tauri registers the same from `exec_path()`, which resolves the same way, and `mainBinaryName` makes the name `Better Mayhem Tracker`. Lane 9 shows that an Electron-written LaunchAgent for the same bundle is left byte-identical and unrewritten. Lane 11 shows the same for a launch through a symlinked folder and through a `..` component. The path stays the same only if T24 puts the Tauri bundle where the Electron bundle was.
- Windows: it depends on T39 and T24. Electron registers `PORTABLE_EXECUTABLE_FILE`, which is the exe the player keeps, `BetterMayhemTracker.exe` as downloaded. After any Electron in-app update the exe is `<dir>\BetterMayhemTracker.exe` whatever the player had named it, because `applyWindowsUpdate` installs under `WINDOWS_EXE_NAME` (`src/main/updater.ts:325`) and relaunches that path. Tauri registers `current_exe()`, unresolved, as `uv_exepath` leaves it on Windows. `mainBinaryName` makes the built exe `Better Mayhem Tracker.exe`. If the release or the hand-off keeps the player's file at `BetterMayhemTracker.exe`, the Run value data is unchanged. If the path changes, the first Tauri launch rewrites the same value name to the new path. That makes one entry, not two, but it resets the StartupApproved value, as Electron does after a move. The shortcut target follows the same rule. This is a parity item for T39 and T24, below.

### For T39 and T24's packaging

The verifier's five points. Each keeps the Run value and the shortcut where Electron left them.

1. The release ships the raw exe as its only `.exe` asset, so the player's file stays one portable exe.
2. No NSIS per-user install. An installer would move the exe under `%LOCALAPPDATA%` and change the registered path.
3. The updater writes the new exe over `dirname(current_exe)\BetterMayhemTracker.exe` and relaunches with exactly that string, so `current_exe()` at the next launch equals the Run value Electron wrote.
4. The Run value name stays the constant `better-mayhem-tracker`, Electron's `app.getName()`, never the product name or the identifier.
5. No installer shortcut. `shortcut.rs` owns `Better Mayhem Tracker.lnk`, and an installer's own shortcut would be a second Start Menu entry.

How the macOS lanes stay off the operator's machine:

- The lane build is a release-profile build, because after T09's tip `install_location` treats only `bmt_release_profile` as installed. It was built with `TAURI_CONFIG='{"identifier":"com.better-mayhem-tracker.lane-t23"}' CARGO_PROFILE_RELEASE_LTO=false CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16 cargo build --release --features custom-protocol`, and kept in `target/lane-release/`, which `cargo test` never touches. It holds the lane identifier once, and `BMT_DATA_ROOT`, `bmt-parity-driver` and `refused to start` zero times. The same binary works before and after the restack.
- A release build has no data root override and no guard. So the script runs it under T06's perf Seatbelt profile (`parity/perf/app.ts` at `fb69c2d`): `(allow default)`, with `file*` denied on both real data folders, on the League install and on `/Users/Shared/Riot Games`, `file-write*` denied on the real `~/Library/LaunchAgents`, and `/bin/ps` denied. The profile is written into the lane folder, and `sandbox-exec` execs the app, so the pid the script kills is the app's. No lane tried a write the profile denies, because the rules forbid that write to the real folders; T06's record owns the profile's proof.
- The lane identifier keeps the single-instance socket, `/tmp/com_better_mayhem_tracker_lane_t23_si.sock`, apart from any installed app's. A launch can never hand over to the operator's app and bring its window forward. The script refuses a binary that lacks the lane identifier. T10's own lock, which arrives with the restack, also keys on the identifier.
- It runs from a scratch `.app` with the bundle id `com.better-mayhem-tracker.lane-t23`, and `HOME` pointing at a scratch folder. Its data folder and LaunchAgents folder both resolve under `HOME`. The script checks that the app logged into the scratch data folder before it trusts a result.
- WebKit ignores `HOME` and keeps website data and caches under the real `~/Library/{WebKit,Caches}/<bundle id>`. The script refuses to run if those folders already exist for the lane id, and removes only those two at exit. None remain.
- Lane 8 runs the parity-driver debug build, copied to `target/lane-driver/debug/` so a later `cargo test` cannot replace it. `tauriBinary({ driver: true })` finds it by its `bmt-parity-driver-v1` sentinel.
